AuroraOS Network Stack

From a bare PCI device to resolving a real domain name and opening a TCP connection: VirtIO-Net, Ethernet, ARP, IPv4, ICMP, UDP, DNS and the TCP three-way handshake — each built as a small, individually verified increment in QEMU.

device virtio-net-pci · runtime qemu-system-i386 · net 10.0.2.15 · gw 10.0.2.2 · dns 10.0.2.3
🌐
AuroraOS now pings the gateway, exchanges UDP datagrams with the host, resolves a real domain name from the internet (example.com → 104.20.23.154), and opens a TCP connection to ESTABLISHED (SYN → SYN-ACK → ACK). The whole L2–L4 stack plus the TCP handshake is live and verified. What remains is TCP data transfer + teardown — then a real GET /. The transport was hardened before any protocol logic, so each layer sits on a proven base with no DMA risk.

What each layer added

Transport & framing

  • PCI discovery + VirtIO-Net bring-up to DRIVER_OK
  • Hardened RX/TX untrusted device fields bounded; drain-loop; IRQ only acks
  • DMA without an allocator identity-mapped static buffers (phys==virt)
  • Ethernet seam EtherType dispatch; IPv6 later = one case
  • Per-interface counters in Settings → System

ARP — a real service

  • 32-entry cache, EMPTY/PENDING/RESOLVED
  • arp_resolve() hides state from callers the API IPv4/UDP/TCP use
  • Learns every sender; answers who-has
  • 60 s TTL, lazy expiry; re-ask after 1 s

IPv4 + ICMP

  • RX accepts only v4 / IHL≥5 / non-fragment / valid checksum / our IP
  • TX: header + payload + checksum, no options/frag/mcast
  • On-link vs gateway routing via ARP
  • ICMP echo both halves we ping out, host can ping us

UDP + DNS

  • udp_send / udp_bind + port demux (no sockets yet)
  • Bidirectional through SLIRP NAT, no hostfwd
  • Typed dns_query(name, type) A today; AAAA/CNAME won't break the API
  • Name-compression-aware answer parser

For the first time in the project, the weak spot is neither the kernel nor the graphics — it is the network above the transport layer, and that gap is now down to a single (large) piece. After UDP and DNS, the layers that build on them — NTP, syslog, discovery — come cheaply; TCP is the last major infrastructure project before AuroraOS can talk to real internet services.

Roadmap

PCI→ VirtIO-Net→ Ethernet→ ARP→ IPv4→ ICMP→ UDP→ DNS→ TCP·SYN→ TCP·data→ HTTP
Next step — Phase 8.2: TCP data transfer
  1. Done (8.1): three-way handshake → ESTABLISHED, on a full TCB + complete RFC state enum (only CLOSED/SYN_SENT/ESTABLISHED active).
  2. Next (8.2): send() / recv() over the open connection — sequence/ack bookkeeping and a receive window — proved by a GET / HTTP/1.0 returning bytes.
  3. Then (8.3): teardown — FIN / CLOSE / TIME_WAIT.
Architecture note.

The stack lives in the kernel for bring-up. As TCP and user-facing networking arrive, resolution and transport move behind the existing netd boundary so TCP is not hard-wired into the kernel — and an x86_64 research branch is worth keeping in mind for when HTTP/TLS and larger workloads start pressing on the i686 ABI. Neither is a migration; both are direction.
