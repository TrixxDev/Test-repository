# Дорожная карта AuroraOS

Цель — пройти путь от текстового ядра до десктоп-ОС в духе macOS со своей
«изюминкой». Ниже — реалистичный поэтапный план. Каждый этап опирается на
предыдущий, поэтому идём по порядку.

## Этап 0 — Загрузка ✅ (готово, v0.1)

- [x] Multiboot1, точка входа, стек
- [x] VGA текстовый терминал, serial-лог
- [x] GDT, IDT, ISR/IRQ, перемаппинг PIC
- [x] Таймер PIT, PS/2 клавиатура
- [x] `kprintf`

## Этап 1 — Память ✅ (готово, v0.2)

- [x] Разбор Multiboot memory map / E820 (сколько RAM, какие регионы свободны)
- [x] Физический менеджер страниц (bitmap-аллокатор кадров 4 KiB)
- [x] Виртуальная память + включение **paging** (рекурсивное отображение)
- [x] Куча ядра (`kmalloc`/`kfree`)
- [ ] Higher-half ядро (перенос ядра в верхнюю половину адресного пространства)

## Этап 2 — Многозадачность ✅ (базово готово, v0.2)

- [x] TSS, переключение контекста (`switch.S`)
- [x] Вытесняющий планировщик (по тикам таймера, round-robin)
- [x] Потоки ядра
- [x] Подготовка ring 3: вход в пользовательский режим
- [x] Системные вызовы (`int 0x80`)
- [x] Процессы с отдельными адресными пространствами (свой page directory на
      процесс), примитив `spawn` (загрузка из ELF)
- [x] `fork`/`exec`, `wait`/`exit` с кодами, очистка ресурсов (см. Этап 4)
- [ ] Несколько потоков на процесс

## Этап 3 — Хранилище и файлы ✅ (готово, v0.3)

- [x] Драйвер диска ATA PIO (LBA28, чтение секторов)
- [x] Виртуальная файловая система (VFS): монтирование, узлы, API драйвера ФС
- [x] tmpfs (in-memory, чтение/запись)
- [x] FAT32 (read-only) для образа диска QEMU
- [x] Загрузка ELF-бинарников с диска и запуск в ring 3
- [ ] Запись в FAT32, кэш блоков, AHCI

## Этап 4 — Unix-подобная модель процессов ✅ (готово, v0.4)

- [x] PCB: процесс = адресное пространство + page directory + таблица
      дескрипторов + состояние + поток
- [x] Жизненный цикл: spawn → running → zombie → reaped, очистка ресурсов
      (адресное пространство, kstack, PCB)
- [x] `fork()` (копия адресного пространства и дескрипторов)
- [x] `exec(path)` (замена образа процесса)
- [x] `wait(pid)` + коды выхода
- [x] Файловые дескрипторы в PCB: `open/read/write/close`, наследование при fork
- [x] STDIO: 0/1/2 на консоль (клавиатура + терминал) через VFS
- [ ] Copy-on-write для fork, несколько потоков на процесс, сигналы

## Этап 5 — Интерактивный shell ✅ (готово, v0.5)

- [x] Зафиксированный syscall-контракт (`include/syscall_abi.h`)
- [x] crt0 + передача `argv` через `exec(path, argv)`
- [x] Shell: `read(stdin) → tokenize → fork → exec → wait → repeat`
- [x] Builtins (`help`, `exit`), фоновые процессы (`&`), обработка ошибок
- [x] idle-поток (IRQ будят заблокированные процессы)

## Этап 6 — IPC и libc ✅ (готово, v0.6)

- [x] Пайпы (`pipe`/`dup2`/`close`), shell поддерживает `a | b`
- [x] `sbrk` (рост кучи), минимальная libc (printf, malloc/free, строки)
- [x] Базовые утилиты (`cat`, `grep`)
- [ ] Редиректы (`>`, `<`), цепочки пайпов `a | b | c`, ещё утилиты

## Этап 7 — Init и сервисная модель ✅ (готово, v0.7)

- [x] init (PID 1): запуск сервисов, супервизия, перезапуск демонов
- [x] logger как отдельный процесс (сервис `log`)
- [x] Message-passing IPC (`msgsend`/`msgrecv`, почтовые ящики)
- [x] Именованный реестр сервисов (`register`/`lookup`)
- [x] Архитектурная документация (`docs/`)
- [x] Reparenting сирот к init; авто-reap фоновых процессов (неблок. `wait`)
- [x] `kill(pid)` и graceful shutdown (shutdown-сообщение → wait → force-kill)
- [ ] Настоящие сигналы, политики перезапуска демонов

## Этап 8 — Инфраструктура (сокеты, безопасность, запись на диск)

- [x] **8A: loopback** (`AF_LOOPBACK`) без сетевой карты — для тестов сокетов
  (v0.8.0). Ядро: `struct socket` (только механизм), `socket`/`sock_link`/`poll`.
  Демон `netd` владеет портами и сводит `bind`/`connect`/`accept` через IPC.
  Проверено `echosrv`/`echocli` (`client → netd → server → обратно`). См.
  [`docs/NETWORKING.md`](docs/NETWORKING.md).
- [x] **netd** как userspace-сервис (стек вне ядра)
- [x] `poll()` для ожидания готовности сокетов
- [x] **8A.5 — базовая безопасность** (v0.8.1, *до* сети): uid +
  `getuid`/`setuid`/`uid_of`; rwx + owner на VFS-узлах (проверка в open/exec);
  права в реестре сервисов (lookup + защита от захвата имени); привилегированные
  порты (<1024) только для root. См. [`docs/VFS.md`](docs/VFS.md),
  [`docs/IPC.md`](docs/IPC.md).
- [x] **8.2 — запись на диск** (v0.8.2): `ata_write_sectors`; FAT32
  read/write (create/grow/overwrite/truncate, обновление FAT и dir-entry);
  `open(O_CREAT|O_TRUNC)`; утилита `save`. Нужно для Finder/настроек/Dock.
- [ ] **8B: сеть** — NIC-драйвер **virtio-net**, затем ARP → IPv4 → UDP → TCP →
  DNS. **Отложено до появления десктопа** (см. ниже). Вне области: TLS, HTTPS,
  IPv6, DHCP, Wi-Fi.

## Этап 9 — Графика (тут начинается «как у macOS») — СЛЕДУЮЩИЙ

> Для ОС в духе macOS визуальный слой важнее сети: пользователь воспринимает
> именно его. Поэтому графика идёт раньше Ethernet/TCP. Главный принцип —
> приложения **не** рисуют в фреймбуфер напрямую: `app → window server →
> compositor → framebuffer`.

- [x] **9.0** Фреймбуфер: линейный RGB-режим (Multiboot 1024×768×32),
  `drivers/fb.c` (v0.9.0). Гейтится: без фреймбуфера — текстовый режим.
- [x] **9.1 (минимум)** 2D-библиотека (`kernel/gfx.c`: rect, rounded rect,
  circle, градиент, blit) + **первый рабочий стол** (`kernel/desktop.c`: обои +
  панель + Dock). `make screenshot` → `aurora_desktop.png`. См.
  [`docs/GRAPHICS.md`](docs/GRAPHICS.md).
- [x] **9.1: текст** — 8×16 bitmap-шрифт (`kernel/font8x16.h` через
  `tools/genfont.py`), `gfx_draw_text`; подписи в меню-баре, часы, буквы на иконках
- [x] **9.0.5: живой вывод — ПОДТВЕРЖДЕНО в QEMU** — Bochs-VBE fallback
  (`make run-vbe`, DISPI + поиск LFB по PCI) и GRUB-ISO (`make iso`). Реальный
  фреймбуфер снят с экрана QEMU (`make live-shot` → `aurora_live.png`). Исправлен
  баг: `pmm_init` не резервировал Multiboot-структуры (info/mmap/cmdline), из-за
  чего командная строка `vbe` затиралась и фреймбуфер не поднимался.
- [ ] 9.1 далее: альфа-смешивание, декодер PNG для ассетов
- [x] **9.2 (event-driven windowserver, ядро core проверено PNG)** Демон
  `user/wserver.c`: единый event loop, единственный писатель в framebuffer, полный
  recomposite на каждый `PRESENT`, протокол окон
  (`WM_CREATE/DESTROY/MOVE/DRAW_RECT/DRAW_TEXT/PRESENT`). Ядро: `fb_map` +
  `fb_active`. **Клавиатура замкнута:** forked reader (`read(0)`) → `WM_KEY` →
  фокусное окно → перерисовка; интерактивный `user/term.c` (Terminal) эхо-печатает
  ввод. `init` в графике запускает windowserver + Terminal (без невидимого shell),
  в тексте — shell. `make screenshot-wm` → `aurora_windows.png`. **ПОДТВЕРЖДЕНО в
  реальном QEMU (v0.9.5).**
  - [x] живой контур (framebuffer + реальная клавиатура + перерисовка на экране) —
    снят с экрана QEMU: `make live-shot`/`make verify-gui` →
    `aurora_live.png`/`aurora_live_typed.png` (видно `aurora> hello aurora_`)
- [x] **9.3 мышь + курсор + click-to-focus — ПОДТВЕРЖДЕНО в QEMU (v0.9.6)**
  ([`docs/INPUT.md`](docs/INPUT.md)): драйвер PS/2 (`drivers/mouse.c`) + IRQ12 →
  сборка 3-байтного пакета → `SYS_MOUSE` → reader-child windowserver → `WM_MOUSE`
  → курсор (рисуется поверх всего) + hit-test (`wm_window_at`) + click-to-focus
  (`wm_raise`). Проверка на экране: `make demo-focus` → `aurora_live_focus.png`
  (клик по заднему окну поднимает его, ввод идёт в него).
- [x] **9.4/9.5 перетаскивание окон + кнопка закрытия — ПОДТВЕРЖДЕНО в QEMU (v0.9.7)**:
  drag-машина состояния в `WM_MOUSE` (`user/wserver.c`): нажатие в title bar
  (`wm_in_titlebar`) → запоминаем окно + смещение курсора → движение при зажатой
  кнопке → `wm_move_clamped` (с ограничением, чтобы окно не ушло за экран/под меню-бар)
  → отпускание завершает drag. Нажатие на красную кнопку (`wm_in_close_button`, с «×»)
  → `wm_destroy` + `WM_DESTROY` владельцу (приложение выходит). Проверка на экране:
  `make demo-drag`/`make demo-close` (+ пиксельные проверки в `tools/verify_drag.py`).
  Затем 9.6 Dock как процесс → 9.7 Launcher/Finder
- [ ] потом (когда десктоп «живой»): client-side surfaces, shared memory,

## «Изюминка» — что выбрать (пока отложено)

> AI-функции **намеренно отложены**. Если делать ассистента — то как
> обычный userspace-демон (`aurorad`), доступный через IPC (реестр сервисов +
> сообщения), **не в ядре**. Сначала нужны сеть и графика.

Главная фишка, отличающая нас от macOS. Кандидаты:

### A. AI-ассистент как системный сервис (userspace)
ОС, где AI — системный демон `aurorad` в userspace: к нему одинаково обращаются
shell, файловый менеджер и GUI через IPC. *Современная дифференциация; требует
сети либо локальной модели — отложено до Этапа 10.*

### B. Необычная метафора рабочего стола
Уйти от «Dock + перекрывающиеся окна» к своей навигации: рабочие
пространства-комнаты, радиальное (круговое) меню по правому клику, тайловый
композитор с жестами. *Чистая UX-дифференциация, целиком в нашей власти, не
требует внешних сервисов.*

### C. Приватность как основа
Всё локально и зашифровано, ноль телеметрии, прозрачный контроль доступа
приложений к данным на уровне ядра. *Сильное позиционирование; требует
продуманной модели безопасности и шифрования с ранних этапов.*

**Можно комбинировать** (например, B + C: необычный UX без слежки). Когда
определишься — зафиксируем выбор здесь и учтём его в архитектуре памяти,
процессов и графики.
